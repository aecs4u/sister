# SISTER — Design, Quality & Data-Consistency Audit

- **Date:** 2026-10-06
- **Target:** SISTER web UI on `http://localhost:8025` (live) and Postgres database `sister` (127.0.0.1:5432)
- **Method:** Playwright MCP (desktop 1440×900, mobile 375×812, light/dark), `psql` consistency queries, source reading for root causes
- **Screenshots:** [docs/audit_2026-10-06/](audit_2026-10-06/)

## 0. Read this first — how the audit was run, and what that limits

1. **The live app on :8025 cannot read Postgres.** `sister/database.py` only builds `sqlite+aiosqlite` engines and uses `sqlite3.connect(DB_PATH)` directly. The only Postgres reference in the repo is `alembic/env.py`, reading the misspelled env var `DATABSE_DSN`. The Postgres `sister` database is therefore, as far as the code goes, a migrated copy (index names such as `idx_3735211_sqlite_autoindex_visura_requests_1`, `text` timestamps with a SQLite `strftime` default are pgloader-style artefacts) and nothing in the app queries it.
2. **During the audit the SQLite file vanished.** `data/sister.sqlite` (+`-wal`/`-shm`) existed at ~16:47 and was gone at 16:48:19 (directory mtime). I only ever opened it read-only; I did not delete it. From that point the live UI showed **0 jobs / 0 documents** (Dashboard, Results, Documents) while Postgres holds 290 requests and 359 documents. The live UI is, at the time of writing, effectively empty.
3. **To compare rendered pages with Postgres anyway**, I copied Postgres → a throwaway SQLite file in the scratchpad (via the app's own ORM tables) and served it from a *second* instance on :8026 with `SISTER_NO_QUERY=1`. UI-vs-DB spot checks below therefore validate the **rendering and query logic against Postgres content**, not a live Postgres connection. The :8026 instance has been stopped; :8025 was never modified.
4. **Side effect I caused:** while probing unauthenticated endpoints on :8026 I called `POST /web/browser/launch-chrome`, which started Chrome with `--remote-debugging-port=9222` and the app's profile `~/.local/share/sister/chrome-profile` (PID 1994363, 16:53:22). Nothing was listening on 9222 beforehand; I sent SIGTERM and confirmed the process tree exited and the port closed. That the call succeeded with no credentials is itself finding S1 below.
5. **Unexplained navigations.** Twice the Playwright tab navigated by itself (`/web/` → `/auth/login?next=/landing`; `/web/results` → `/web/documents`). I found no auto-navigation in the app's JS and could not reproduce it under a controlled run, so I did not count it as an app defect. Possibly another driver of the same browser.
6. **Colour contrast:** my automated contrast scan could not see gradient/CSS-variable backgrounds and produced false positives (e.g. white text on the blue primary button). Only contrast problems I confirmed on screenshots are listed.
7. Browser-automation (portal) flows were not exercised, per `CLAUDE.md`.

## 2. Database audit (Postgres `sister`)

**Overview:** 49 user tables + 6 views, 52 MB, 29 tables empty. `alembic_version = 20260908_normalize_payloads`.

Populated tables: `cadastral_locations` 1287 · `cadastral_subjects` 87 · `visura_requests` 290 · `visura_responses` 271 · `visura_results` 75 · `visura_properties` 2345 · `visura_owners` 303 · `ownership_rights` 24 · `visura_documents` 359 · `document_metadata` 309 · `document_xml_nodes` 20 550 · `document_xml_attributes` 37 916 · `page_visits` 911 · `page_visit_form_elements` 6790 · `page_visit_errors` 67 · `sister_owner_index` 306 · `sister_property_index` 2608.

### What is consistent (checked, zero violations)
- 52 FK constraints, no violations. No responses without requests; no results/properties/owners pointing at missing responses, results, locations, subjects or rights.
- No duplicate `cadastral_locations` rows on the natural key; no duplicate subject fiscal codes.
- `success`/`error` agree (no success with error text; no failure without error text); no non-JSON `data` payloads.
- Documents: all 359 `file_path`s exist on disk and every `file_size` equals the on-disk size. 356 distinct files + 3 duplicate rows (see D2). Three `*.plan.json` files on disk are not in the DB (expected derived artefacts).
- Headline counts match the UI: 290 requests, 216 successful (110+62+44), 55 failed, 19 without response ("Pending").

### Findings

**D1 — Application and database are decoupled (Critical).** See §0.1. Also `.env` has `DATABSE_DSN` / `DATABSE_DSN_NEON` (typo for DATABASE) and `SISTER_DB_PATH` pointing at SQLite; the Neon DSN contains a live-looking credential in plain text in `.env` (ensure `.env` is git-ignored and rotate if it was ever committed).

**D2 — Documents are not linked to requests (High).**
- `visura_documents.response_id` is NULL for **359/359** rows.
- `get_documents_for_response()` (`sister/database.py:846`) therefore falls back to matching `CadastralLocation.sheet == foglio AND parcel == particella` — **ignoring province, municipality and cadastre type**. Sheet/parcel pairs occurring in several municipalities exist (e.g. 103/1714 in 4, 80/1964 in 3, 100/50 in 3).
- Consequence, observed in the UI: request `req_F_38c562d8…` (Ravenna F101 P2) lists **83 "Downloaded Documents"**, and the *same 83* appear on all **48** requests for that parcel.
- 3 filenames exist twice (`vi_sto_PA_FG134_PT122_SUB5.pdf`, `…SUB21.pdf`, `vi_sto_RA_FG101_PT2_SUB15.p7m`, each 2×, same `file_path`); `visura_soggetto` F101/P2/Sub61 exists 6× per format; F134/P122/Sub21 5×.
- 50 documents have no `document_metadata` row; 4 metadata rows have `location_id = NULL`.
- `visura_documents.subject` is empty for all 359 rows; `requested_at` is populated for 31 only, in two formats (`12/04/2026 15:44:06` vs `2024-10-29`).

**D3 — Location data is not normalised (Medium).** `cadastral_locations.province`: 924 empty, `Ravenna` 139 vs `RA` 82, `Roma` 85 vs `RM` 39, `PALERMO` 5 vs `Palermo` 1 vs `PA` 2. 99 sheets are non-numeric with prefixes leaking in (`C/100`, `S/101`, `RA/103`) which creates distinct "locations" for the same parcel. 9 rows have `cadastre_type` NULL/empty. **9 rows store a fiscal code in `parcel`** (soggetto/persona queries reuse the column); the Results table and the detail page then show a fiscal code under "Particella". `cadastral_subjects.subject_type` is NULL for 86/87 rows; 6 subjects have no fiscal code (`COMUNE DI ROMA` ×3, `INTESTAZIONE PARZIALE` ×3 — three duplicates of each because the natural key is missing).

**D4 — Result counts disagree (High).** For 126 successful responses `total_results` ≠ `count(visura_results)`: `visura_results` holds only 75 rows, while `visura_properties` holds 2345. For `req_F_38c562d8…` `total_results = 64`, `props = 64`, `json immobili = 64`, `visura_results = 0`. The properties are consistent with the JSON; `visura_results` is simply not populated for most responses. Any consumer joining through `visura_results` gets empty data. Also `total_intestati` is NULL everywhere I looked and `visura_owners` is empty for owner-less soggetto queries, so owner counts rely on JSON, not the normalised tables. The ownership title ("Nuda proprietà per 1/1", "Proprietà per 1/1") shown in the UI is **not stored** in `visura_properties` (no column); only 24 `ownership_rights` rows exist.

**D5 — Failed-request quality (High/Medium).** Of 55 failures: **49** `'VisuraPersonaGiuridicaRequest' object has no attribute 'tipo_ricerca'` (a code defect, not a portal failure), 4 re-auth failures (`Target page, context or browser has been closed`), 1 locator timeout, 1 session-expired page. Also, a "success" can be semantically empty: `wf_search_Roma_872_405_6b278542` is `success=1` with `error` NULL, but its JSON payload says `"error": "NESSUNA CORRISPONDENZA TROVATA"` — the UI shows it as **Completed** with "0 results". There is no "no match" status, and the *Partial* status card is always 0.

**D6 — Timestamps (Medium).** `visura_requests.created_at` and `visura_responses.created_at` are `text` (mixed `2026-09-25 16:10:05.99` and `2026-09-08T21:58:26.61`: 270 vs 20 rows), while `visura_documents.created_at` is `timestamptz`. Naive text is sorted lexicographically by `find_result_rows` (`ORDER BY` in Python on the string) so the two formats interleave incorrectly. Same job, different clocks: request 16:10, response 16:27 (text), page-visit timestamps 18:27 (converted to local by the new code in `_parse_page_visits`) — a 2-hour skew visible on one detail page.

**D7 — Schema drift and migration hygiene (Medium).**
- Alembic head in the repo is `20260925_sezioni_jobs` (untracked file); Postgres is stamped `20260908_normalize_payloads`. The table `sezioni_extraction_jobs` already exists (0 rows, `text` timestamps) so it was created outside alembic.
- ORM vs Postgres column mismatch (found when copying data): `document_subjects`, `building_identifiers`, `related_parcels`, `land_parcels`, `ownership_mutations`, `property_owners`, `legal_entity_search_properties`, `feedback_unsubscribes` have different shapes in Postgres (denormalised columns instead of `subject_id`/`location_id`/`right_id`; `feedback_config` has extra `cc_emails`, `bcc_emails`, `invitation_bullets`). All are empty, so no data loss, but code writing to them would fail on Postgres.
- Objects not in the ORM: tables `immobili`, `intestati` (legacy, empty), `sister_owner_index`, `sister_property_index`, and views `v_sister_*` (DBeaver is actively querying `v_sister_owner_context`).
- Missing FKs: `visura_requests.location_id`, `visura_properties.location_id/subject_id`, `visura_owners.subject_id/right_id` have indexes but **no** FK. Orphan checks currently pass, but nothing enforces it.
- Duplicate index on `document_metadata.location_id` (`…_ix_document_metadata_location_id` and `…_idx_document_metadata_location`). 14 indexes still carry `sqlite_autoindex` names, and most columns are `text`/`bigint` where `varchar`/`boolean`/`timestamptz` were intended (`success` is `bigint`).
- 19 requests have no response row (UI "Pending") — some are 2026-06 data, i.e. permanently stuck rather than pending; there is no `status`/`completed_at` column on `visura_requests` to distinguish queued, running and abandoned.

**D8 — PII at rest (note).** Fiscal codes, birth dates and places of natural persons are stored in clear text in `cadastral_subjects`, `visura_responses.data`, and `document_xml_*`, and are rendered in full on the detail and dossier pages with no masking. Confirm lawful basis / retention (the "Privacy Policy" page exists; `cleanup_old_responses` only applies to cached responses).

## 4. Functional / backend defects

**B1 — `POST /web/documents/rescan` → HTTP 500.** `sister/utils.py:1796` does `from .db_models import DocumentXmlAttribute, DocumentXmlNode`, but `DocumentXmlAttribute` is defined in `sister/visura_xml_models.py:61` (database.py imports it from there). Any rescan that needs to back-fill XML metadata crashes. Matches the 50 documents with no metadata. (`ImportError` confirmed in the instance log.)

**B2 — `bootstrap is not defined`** on `/web/forms` (inline script at ~line 5495 runs before the Bootstrap bundle executes). Tooltips/popovers on that page silently fail. Bootstrap, Tabulator and others come from `cdn.jsdelivr.net` (CSP allows it) — the app degrades or breaks offline.

**B3 — Error display.** Failed form submission shows `Error: Servizio non inizializzato` plus a second block with the raw `{"detail": "Servizio non inizializzato"}` JSON. English prefix + Italian message, raw JSON in a user-facing area. Status 503 is appropriate; the presentation is not.

**B4 — Default credentials.** `main.py:296-297` falls back to `demo@aecs4u.com` / `demo123` when `AUTH_USERNAME` / `AUTH_PASSWORD` are unset, and the code path is active whenever `USE_CLERK_AUTH=false` (current `.env`).

**B5 — Redirect parameter mismatch.** The auth redirect handler builds `/auth/login?next_url=…` while the navbar "Sign In" link and login form use `?next=…` (observed: `next=/landing`, hard-wired, regardless of the current page). After login the user cannot be returned to where they were.

**B6 — Auth static assets broken.** On `/auth/login`, `/auth/forgot-password`, `/auth/reset-password`: `/static/aecs4u-auth/css/{design-tokens,components,auth}.css` return JSON (MIME `application/json` → refused), `/static/aecs4u-auth/js/theme.js` and `favicon.svg` 404. The login page still renders acceptably but is off-brand — a purple gradient unlike the AECS4U blue theme — and theme switching does not work there. 4–5 console errors per auth page.

**B7 — 404 handling.** `/web/nonexistent` returns a bare JSON `{"detail":"Not Found"}` (22 bytes, no HTML, no navigation) while `/web/results/<unknown>` returns a full branded HTML 404 (17 KB). Inconsistent; the JSON one is a dead end for a browser user.

**B8 — `/web/files` and `/web/documents` render the identical page** (both titled "Documenti", 446 chars, same content in the unauthenticated empty state; the code registers `/web/files` as a second route). Duplicate URL, duplicate nav label.

## 5. Security observations

(Evaluated on a throwaway instance; `.env` currently sets `REQUIRE_AUTHENTICATION=false`.)

**S1 — Mutating routes are reachable without authentication when `REQUIRE_AUTHENTICATION=false`:**

| Route | Result without credentials |
|---|---|
| `POST /web/browser/launch-chrome` | **200 — spawned Chrome with CDP :9222** (confirmed, see §0.4) |
| `POST /web/results/refresh` ("Import Outputs") | 303 (imports files from `outputs/` into the DB) |
| `POST /web/documents/rescan` | 500 (reaches the handler; would write to DB) |
| `POST /visura/queue/clear`, `POST /web/browser/stop`, `PUT /api/v1/admin/feedback/config`, `POST …/send-invitations` | 503 (blocked only because the service was down, not by auth) |
| `POST /shutdown` | present in OpenAPI; not invoked |

The service listens on `0.0.0.0:8025` (`scripts/start.sh` / uvicorn flags), so anyone on the LAN can start a browser on the host, trigger imports or clear the queue. Recommend: refuse to start with auth disabled unless bound to 127.0.0.1; protect `/shutdown`, `/web/browser/*`, admin routes with a separate admin check regardless of `REQUIRE_AUTHENTICATION`.

**S2 — Path traversal: not found.** `/web/documents/view/..%2F…/etc/passwd`, `/web/dossiers/view/…`, `/web/dossiers/…?download=1`, `/web/documents/…`, `/static/../../.env` → all 403/404. `/web/files/../..` → 301 (normalised). Good.

**S3 — Headers:** HSTS, `X-Frame-Options: DENY`, `nosniff`, Referrer-Policy, Permissions-Policy present. CSP allows `'unsafe-inline'` and `'unsafe-eval'` for scripts and many third-party origins (tailwind CDN, clerk, stripe, maps, holoviz) that SISTER does not use; HSTS is sent over plain HTTP on localhost. CORS: no `Access-Control-Allow-Origin` returned for a foreign origin (good).

**S4 — `window.confirm("Import exported JSON files from outputs/…")` is the only guard on a state-changing action**, and the button is visible to unauthenticated users in this configuration.

## 6. Design & UX audit

Screenshots: [results](audit_2026-10-06/results2.png), [detail](audit_2026-10-06/detail_soggetto_E_0.png), [documents](audit_2026-10-06/documents2.png), [dark results](audit_2026-10-06/dark_results.png), [dark forms](audit_2026-10-06/dark_forms.png), [mobile documents](audit_2026-10-06/m__web_documents.png), [mobile results](audit_2026-10-06/m__web_results.png), [login](audit_2026-10-06/login.png), [dossiers](audit_2026-10-06/dossiers.png).

### Visual / layout

**U1 — Dark mode is broken on data-heavy pages (High).**
- *Results:* the Tabulator grid keeps a **white background** while text takes the dark-theme light colour: row numbers, Catasto, Provincia, Comune, Foglio, Particella are almost invisible on alternate rows; header labels are washed out; Request-ID links sit in black chips.
- *Query Forms:* the "Query Types" panel is a white box with an invisible heading and "Select Endpoint" label; radio labels "Property Data" / "Owner Lookup" are pale-on-white; the sidebar icons for *Cadastral Map, Elaborato Planimetrico, Original Records, Inspections* are dark-on-dark and disappear.
- *Documents / Dossiers (esp. mobile):* accordion headers ("Visura per Immobile", "Fabbricati · Attuale") are white-on-white.
- *Browser Control:* several badges/buttons 2.1–3.9:1.
- Guide, Glossary and static pages are fine in dark mode, which shows the problem is in page-specific CSS and third-party widgets (Tabulator theme not switched).

**U2 — Wide tables are clipped with no visible affordance (Medium).** On the detail page, the Immobili tables (Catasto…Particella… cut after "Particell"), Page Visits (the *Errors* column is cut) and the DB Immobili grid ("Indirizzo" cut); on Documents, the table is cut after "DATA RIFERIM". There is a `maxHeight: 600px` + `fitDataFill` grid with a horizontal scroll that is not obviously visible. Results' last columns (*Extracted response, Status, Date*) are off-screen at 1440px with the sidebar open.

**U3 — Documents hero header (Medium).** A near-black hero band in the light theme clashes with the rest of the page. Inside it: breadcrumb "Dashboard" (grey on dark, underlined, low contrast), the green "Esporta con nomi" button (dark green text on dark — visibly the weakest), and the **hero action buttons (8) wrap to 2 lines ("Sfoglia file", "Esporta con nomi")** and overflow on mobile (the "Dossier" button is cut off at 375px).

**U4 — Detail page structure (Medium).**
- The same data appears **twice** ("Immobili (5)" from JSON, then "Immobili (5) DB").
- "Total Results" and "Skipped Soppresso" each occupy a full card for a single digit.
- Raw JSON keys leak into labels (`CODICE_FISCALE`, `SELECTION_VALUE`, `DISPLAY_NAME`, `DATA_DI_NASCITA`); `SELECTION_VALUE` exposes the portal's internal token (`9713834997#0#LA VARDERA#…`).
- "Catasto" column says **F** for each property while the request's Catasto badge says **E**.
- "FOGLIO / PARTICELLA: – / LVRSML93H08G273J" (D3).
- Internal terms in English ("Request Details", "Page Visits", "Raw JSON", "Extracted response") next to Italian labels ("Titolarità", "Ubicazione").

**U5 — Results page (Low/Medium).**
- Header filters in Tabulator duplicate the filter bar above (two filtering mechanisms with different semantics: server-side vs client-side on the current page only).
- Columns "C.", "F.", "P.", "I." are cryptic abbreviations, truncated in the header ("C…", "I…", "S…").
- Request IDs are cut to 20 characters + "..." so the type/date information at the end of the id is lost (full id only in the link tooltip).
- Status "Partial" card is always 0 (no code path produces it).
- "Page 1 / Next" pagination with an unknown total number of pages; "Showing 1–200 of 290" is correct but no page count.
- Page weight at limit=200: 165 KB HTML; Documents page 414 KB HTML for 184 rows (all rendered server-side, no virtualisation). Fast locally (≤ 41 ms) but will degrade as data grows.

**U6 — Time handling (Medium).** Documents shows `2026-10-06 14:44` (UTC) for a file created at 16:44 local; Results shows naive local-time strings; page visits are shifted again. No timezone label anywhere. For an Italian-audience product, display in Europe/Rome and label it.

**U7 — Navigation (Low).** Sidebar item "Browser" has no icon (all others do). Labels are English (Dashboard, Query Forms, Results, Documents, Dossiers) but the destination pages are Italian (Documenti, Dossier). `Documents` vs `Dossiers` are easy to confuse and `/web/files` is a third alias. Navbar shows a **"Sign In" button** even though no login is required (auth disabled).

### i18n / content

**C1 — Language mix.** `<html lang="en">` on the production pages (the throwaway instance served `lang="it"` for some pages), while the content is mostly Italian; the language switcher says "English"; the cookie banner is English ("Cookie Policy… Accept All/Decline") although the markup contains the Italian "Informativa sui cookie" (it is swapped by JS → visible flash/mismatch); Query Forms is fully English ("Property Search", "Submit Request", helper text); Guida/Cheat sheet/Glossario are Italian. Screen readers will mispronounce Italian content.

**C2 — Missing meta description** on every page (no `<meta name="description">`); titles are generic (`SISTER - Results`) and never include the entity being viewed except the detail page.

### Accessibility

Positives: skip-link first in tab order, landmarks (`main`, `nav`, `footer`), one `h1` per page, visible focus indicators (box-shadow/outline), form labels on all visible fields, 0 images without alt, ARIA labels on icon buttons in the top bar.

Gaps:
- **A1** Heading hierarchy skips: Dashboard `h1 → h3 (stat values) → h5`; Query Forms `h1 → h5 ×~60`; Dossiers `h1 → h3`; the stat "numbers" are `<h3>`s (headings used for styling).
- **A2** Query Forms contains **23 `<form>`s / 142 controls** in one DOM (hidden ones inflate the accessibility tree); the hidden `csv_data` textarea and `file-input-batch` have no label.
- **A3** `/auth/reset-password` has 2 buttons without an accessible name (likely the show/hide-password toggles) and **no `h1`** on `forgot-password`/`reset-password`.
- **A4** Cookie modal has no `role="dialog"`/`aria-modal` (checked while hidden; its markup has neither), so focus is not announced/trapped.
- **A5** Mobile touch targets: 154 interactive elements < 24 px on Results (Tabulator header filters, sort arrows), 109 on Documents.
- **A6** Several Tabulator cells are clickable rows (`rowClick` → detail) with no keyboard equivalent besides the ID link.
- **A7** Colour alone distinguishes status badges in the table (also fails contrast on some themes — `bg-success` badge text measured 2.5:1 by script; not visually confirmed, verify).
