## 0. Scope, constraints, caveats

- **Strictly read-only.** Only GET requests were sent to the app. For form and table tests every non-GET request was blocked in the browser (`page.route`), so no query, workflow, purchase, rescan or browser-control action ran.
  A wrong-password login (fake user) was submitted once, to check the error path.
- **A live batch was running during the audit.** `sister batch run-session … master_npl_partner_companies` was running against a second service on port 8027, with load average ≈ 4.6 and the same PostgreSQL. All timings below are therefore *pessimistic*; each timing finding says how it was measured and how much of it may be load. I did not touch that run.
- **Only the admin role was exercised.** The demo/regular-user view (hidden admin links, 403 on `/browser`) and the purchased-documents flow were not re-tested; the plain-text password file was not opened.
- **Not tested:** CAPTCHA flow, query submission, PDF export content, printing, the 3D/KMZ viewer interaction, Leaflet map interaction, tag editing / bulk tagging (writes), notes, favourites toggling (writes), screen-reader output, real-device touch, Safari/Firefox.
- **Contrast numbers** are computed from computed colours; the script skips elements on gradients (so the white-on-gradient hero buttons are not judged). One apparent hit (F4) was checked by hand and is real.
- **Privacy:** several screenshots show real subjects (names, tax codes, a notarial act). `*.png` is git-ignored; do not share the folder.

### What is good (so it is not lost)

- **No script errors anywhere.** 0 console errors/warnings and 0 `pageerror`s on 38 URLs × 3 renderings, except the expected 404 resource line on the 404 page. 0 failed requests apart from two navigation-aborted images.
- **Accessibility baseline is solid** and fixes from 2026-10-09 held: 0 unnamed interactive elements, 0 unlabeled form controls, 0 images without `alt`, 0 duplicate ids, **0 inline event handlers**, **0 inline `<script>` without a nonce**, `<main>` landmark on every page, `lang="it"` on every page except the 404.

## 2. Findings

### F1 🔴 Subject-visura pages crash (HTTP 500) — template name collision

**Reproduction:** open `/documents/2070` (or `/documents/1`, `/documents/2069`) as an admin. The page never renders; the themed error page arrives after ~75 s.

**Evidence (`logs/visura.log`):**
```
File ".../sister/templates/catasto/_ownership_history.html", line 7, in top-level template code
    <span class="badge …">{{ ownership_history|length }} immobili</span>
TypeError: object of type 'Macro' has no len()
  web.py:9784 web_documents → web.py:5600 _render_doc_from_db → theme.render("catasto/entity.html", …)
```
**Cause:** [`web.py:5611`](../sister/web.py) passes `ownership_history=` (a list) into the context, and [`entity.html:179/211`](../sister/templates/catasto/entity.html) includes `_ownership_history.html` under `{% if ownership_history %}`. But `entity.html` extends the theme's `catasto/visura_base.html`, whose line 19 does `{% from "catasto/visura_story.html" import property_history, ownership_history %}`. In the extending/included template the *macro* wins over the context variable, so `ownership_history` is a `Macro` (truthy, no `len()`).

**Scope:** every page rendered through `_render_doc_from_db` → `entity.html` with a stored visura (documents 1, 2069, 2070 reproduced; property visure such as `/documents/387` are unaffected). `/persons/<cf>` and `/companies/<piva>` *without* a stored visura use `_render_query_only_subject` and render (verified on RIZZO FRANCESCO and 05828330638); the 53 persons "con visura archiviata" almost certainly crash through the same path (not individually opened).

**Fix:** rename the context variable and the template references (e.g. `subject_ownership_changes`) at `web.py:5611`, `web.py:11768`, `entity.html:179,211`, `_ownership_history.html:7,13`. Add a regression test that renders `catasto/entity.html` with a stored-visura document and a non-empty history (the current `tests/test_ownership_history.py` evidently does not render through the theme base).

**Second problem on the same URL — the error takes 60–75 s to reach the client.** The exception is logged < 1.5 s after the request arrives, yet the 500 HTML (7.8 KB) arrived after 75.7 s in one run and the Playwright navigation timed out at 30 s in another. I did not find the cause (candidates: the error handler's `theme.render("error.html")`, or the request being queued behind the work in F2). It should be traced separately: a failing page that hangs for over a minute is worse than a failing page that fails fast.

### F2 🟠 One slow request starves unrelated pages

**Measurements** (desktop sweep, TTFB / load; the same pages answered in the ranges shown when the server was idle):

| Page | Slow run | Idle |
|---|---|---|
| `/admin` | 40.6 s / 40.8 s | 40–150 ms |
| `/admin/documents` | 30.5 s | 0.3 s |
| `/valuation` | 29.9 s | 0.3 s |
| `/dossiers/view/immobili.json` | 31.0 s | 0.15 s |
| `/companies/` | 27.8 s | 0.4 s |
| `/favorites` | 9.8 s | 0.3 s |
| `/persons/` | 6.1 s | 0.3 s |
| `/admin/commands` | 16.6 s | 0.3 s |
| `/` (Dashboard) | 2.9 s (also 30 s once on mobile) | 0.1 s |

The slow runs immediately followed `/persons/<cf>` and `/companies/<piva>`, which start a background **parcel-map build** (`web._hub_parcel_map`); the log shows `GET /companies/12781710962/parcel-map.json - 200 (39481 ms)` and `(34753 ms)`, and `GET /documents/387 - 200 (32584 ms)`. Pages that do no work of their own were delayed by the same amount, which points to blocking (synchronous CPU/DB/geocoding) work on the event loop or an exhausted thread pool, not to slow queries in those pages. The concurrent batch and a load average of ≈ 4.6 amplify it, so absolute numbers are pessimistic, but the *pattern* (unrelated pages inheriting another request's duration) is the finding.

**Also measured directly:** `/persons/RZZFNC41D15H519A` 20.8 s for 283 KB of HTML; `/companies/05828330638` 25.6 s TTFB, 44 s to `load`, 14,685 DOM nodes.

**Suggestions:** run the parcel-map build in a worker process / `run_in_executor`, make sure every DB call is async, cap concurrent heavy renders, add a request-duration log with the event-loop lag, and give the hub a server-side summary instead of 283 KB / 15 k nodes of HTML (see F10).

### F3 🟠 Desktop sidebar cannot be re-opened without reloading

**Reproduction (≥ 992 px):** with `localStorage.sidebarHidden = "true"` (the state the toggle itself saves when you hide the sidebar), load any page → sidebar is hidden → click the hamburger. `body` flips to `sidebar-visible` and `localStorage` to `false`, but `#sidebar` stays at `left: -280px; visibility: hidden` (checked 700 ms and 1500 ms after the click, three times). A reload then shows it.

**Cause:** the pre-paint script in [`_base.html:16`](../sister/templates/_base.html) adds `html.sidebar-pref-hidden`, and [`sister.css:387`](../sister/static/css/sister.css) forces `html.sidebar-pref-hidden body.sidebar-visible .sidebar { transform: translateX(-100%); visibility: hidden }`. Nothing ever removes `sidebar-pref-hidden` (no JS references it), so the override outlives the first paint.

**Fix:** remove the class once the toggle script runs (or on `DOMContentLoaded` + one frame), or scope the rule with `:not(.sidebar-toggled)`.

**Related (mobile):** `#sidebarToggle` reports `aria-expanded="true"` while the off-canvas sidebar is closed (value is inverted on load at 375 px), and **Esc does not close** the open off-canvas sidebar. A tap target outside the sidebar is the only way to dismiss it. `[shot: v_m_sidebar_open]`

### F4 🟠 Invisible full-width buttons at the bottom of property-visura pages

They sit after the footer and are invisible but focusable, so keyboard users tab into three unlabelled-looking stops, and the page ends with a ~120 px blank band. The visible hero of the same page has none of these actions, while the *subject* page does (`Documenti · Report completo · Social · Invia email · Stampa`). The theme's share/print toolbar is apparently rendered outside the hero. `[shot: d1440_light_document_detail]`

### F7 🟠 404 page loses the shell, user and language ↩ (10-09 F10 only half-held)

## 3. Visual design & UX review (page by page)

### 3.1 Dashboard `/` `[shot: d1440_light_dashboard]`
- **Left column is a half-empty card:** "Azioni rapide" ends after one paragraph while "Attività recenti" is ~850 px tall → ~450 px of dead white.
- **Recent activity rows overflow semantically:** a completed row lists *every comune* of a 197-result search inline ("Bergamo · Brescia · Cremona · …", 11 lines) and its timestamp wraps to three lines (`2026-` / `11-05` / `19:18`). Truncate to "N comuni" with a tooltip/expand and give the date a `white-space: nowrap` column.
- **Dates are ISO** (`2026-11-05 19:21`) here, on Results, and in the subject header, but `dd/mm/yyyy` on documents and the `it_date` filter elsewhere. Pick one (the Italian one).
- Five KPI cards are fine and aligned. "Senza corrispondenza" (1.336) uses an orange "?" and "Fallite" red ✕ — good affordance.

### 3.2 Query `/forms` `[shot: d1440_light_forms]`
- **One flat 14-field form.** The *provisional identifier* fields (Tipo denuncia, Numero denuncia, Anno denuncia, Identificativo tipo) and `Richiedente`/`Motivo` are always shown, even though most users never fill them. Group them under "Avanzate".
- **Provincia/Comune are free text** (no `<datalist>`, no autocomplete — checked: `list=null`, 0 options) although the portal needs an exact name, and the page itself says "Nome della provincia: seleziona l'ufficio SISTER". Autocomplete from the ISTAT list that the app already has.
- The "Seleziona la ricerca" radio group renders **three large option cards with undersized, low-contrast radios** (the selected one overlaps its label; unselected ones are almost invisible). The 13 px `btn-check` inputs behind the segmented controls (`Passo singolo / Multi-step`, `Singola / Batch`) are also flagged as < 24 px, though the visible labels are fine.
- Native validation works and **blocks submission** (no request left the page): the browser bubble "Completa questo campo." appears on `provincia` first. There is no inline summary of all missing required fields (5 are `:invalid`).
- Required fields use a red asterisk with no legend; "T = Terreni, F = Fabbricati, E = entrambi" help text should be the option labels themselves (`Terreni / Fabbricati / Entrambi`) instead of a "—" default that then needs the legend.

### 3.3 Results `/results` `[shot: v_results]`
- Stat cards misalign: labels that wrap ("Richieste eseguite", "Senza corrispondenza") push the number down 20 px relative to their neighbours.
- Good: the explicit sentence "I filtri nell'intestazione agiscono sulle 50 righe di questa pagina; per cercare tra tutte le 6.211 richieste usa il modulo qui sopra." That honesty is rare. But two filtering systems (form + header filters) with different scope is inherently confusing; consider making the header filters server-side like `/persons`.
- Tabulator header-filter placeholders are cut ("Filtr…", "Filtra pe…") in narrow columns.
- No keyboard sort: Tabulator column headers have `role="columnheader"`, `aria-sort="none"` but **no `tabindex`**, so sorting is mouse-only (same on `/persons`, `/companies`).

### 3.4 Result detail `/results/<id>` `[shot: v_result_detail]`
- **Raw keys as headings:** table columns show `codice_fiscale`, `selezionato`, `indice`, and the cells show `false`; the same table also has a second `Denominazione` column next to `denominazione` (duplicate data, different casing). `omonimo*`, `incompleta` etc. render as individual cards with a tag icon and a single value ("Ambito: NAZIONALE", "Totale risultati: 197"), eleven sections where four would do. Map technical keys to labels (the `display.py` filters already exist) and merge scalar sections into one summary list.
- The section pill bar is useful, but "Soggetto" is 1.63:1 in dark mode (F5).
- Page is 10.5 k px / 4.6 k nodes for 197 rows: paginate server-side or collapse tables by default.

### 3.5 Documents `/documents` `[shot: v_documents]`
- **Pagination is unstyled text** ("Prima  Precedente  Pagina 1 di 11  Successiva  Ultima") in one grey/blue strip; Prima/Precedente look like disabled blocks, the rest like links. Use Bootstrap pagination.
- "Filtri e ordinamento riguardano la pagina corrente" — filters operate on 100 of 1,064 documents. Same remark as Results.
- The "Tipi di documento supportati (10)" accordion repeats the category chips below it (5 of the 10 types have count 0). 112 text nodes are < 12 px on this page.
- Toolbar: 7 buttons in two rows with different visual weights ("Aggiorna archivio" is the only yellow-outlined one with a caret).

### 3.6 Document detail `/documents/387` `[shot: d1440_light_document_detail]`
- Clean and readable; the 10-09 parsing fixes held (requester, dates `30/01/2025`, money `€ 52.000,00`). Section D text is capital-letter prose in a table cell: set it in a normal reading column.
- Ghost buttons: F4. Three `<summary>` elements ("Dettagli tecnici", "Payload JSON originale", "Testo completo estratto dal PDF") are 17–21 px high.

### 3.6b Subject page `/persons/<cf>` `[shot: v_person_top]`
- Strong header (name, birth, age, KPIs, "valore catastale è la base IMU, non un valore di mercato" — good honest wording).
- **Headline numbers disagree on the same screen:** "VALORE CATASTALE PRO QUOTA **1.229.442 € ***" (with "intero 1.232.629 € · +20 n.v.") versus the card below "Valore catastale · quota **€ 1.226.803**". The `*`/`n.v.` footnote explains part of it, but the two figures sit within 600 px of each other with different bases. Label the second as "(solo immobili valutati)" or reconcile.

### 3.7 Persons / Companies list `[shot: v_persons]`, `[shot: v_m_persons]`
- Toolbar is the weakest part: search box, "Tutti i nominativi" select, "Tutti i tag" select, three separate collapsed `<details>` (`Gestisci i tag…`, `Colonne`, `Come leggere le colonne`) and a floating "Classifica:" chip group sit at five different left/baseline positions. A single toolbar row (search · filters · ranking menu) with one "Altro" popover would remove ~150 px of vertical noise.
- On mobile the five KPI cards take **three rows (~560 px)** before the list; the 5th is orphaned. Make them a 2-up compact strip or collapse behind the title.
- Table ★ buttons are 20×18 px; "Solo le principali / Tutte" 23 px high.
- The company list's first-load TTFB was 27.8 s under load (F2), the person list 6 s.

### 3.8 Admin `/admin` `[shot: v_admin]`
- Page title (`x=336`) is indented 12 px relative to the card grid (`x=324`) — different containers.
- Five cards, the last orphaned on a second row; "Regola di accesso" is a card with no action. "Riconcilia file e catalogo" is a secondary button whose label reads as disabled (grey on white).

### 3.9 Info/legal pages
- **Titles are inconsistent:** `SISTER - …` (most), `Informativa sulla privacy - AECS4U`, `Impostazioni - Sister`, `Accesso — SISTER`.
- **Privacy and Terms expose an environment variable name** (`SISTER_GEOCODING`) in user-facing copy. Say "la geocodifica può essere disattivata dall'amministratore".
- `/privacy` heading order skips (h1 → h5 → h3 → h4 → h3 …), 26 targets < 44 px.

### 3.10 Login `[shot: v_login_d]`, `[shot: v_login_wrong]`, `[shot: v_login_m]`

## 5. Security & hygiene observations (from the browser)

- Headers and fail-closed auth as listed above; `HEAD /health` returns **405** (`logs/sister.log`), which some load-balancer/uptime checkers use — accept `HEAD`.
- `/docs` redirects (302) but `/openapi.json` answers **401 JSON**, a small inconsistency; neither leaks anything.
- The 500 error body is an HTML page with no stack trace. A correlation id is logged (`id=…`); showing it on the page would shorten support loops.
- The login page logs a 401 on every logged-out load (noise in any real-user-monitoring).
- Local passwords were not inspected (see memory note on the plain-text `local_users.txt`).
