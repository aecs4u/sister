# Catasto API gap analysis: SISTER and Openapi Catasto

**Assessment date:** 2026-11-03
**Scope:** SISTER's own HTTP API and client in `sister/main.py`, `sister/client.py`, and `sister/query_forms.py`, plus related authenticated JSON routes in `sister/web.py`. This is a source and contract comparison; it does not claim live runtime or provider-account verification.

## Executive summary

SISTER and Openapi Catasto overlap in cadastral searches, subject/property queries, visure, mortgage inspections, map documents, and elaborati planimetrici. They are **not API-compatible**: SISTER submits work to its local queue and automates SISTER portal forms, while Openapi Catasto exposes its own bearer-authenticated service, resource paths, request schemas, and result/document lifecycle.

The largest remaining gaps are authoritative court/Conservatoria catalog data, standalone monitoring, and direct Geo Catasto lookups (`/foglio` and `/particella`). SISTER now has local territory and office route families, but the court and Conservatoria catalogs still need an authoritative import. SISTER's map views and JSON payloads remain tied to stored people, companies, or documents and do not provide the same general-purpose lookup contract.

If the goal is to add Openapi Catasto as a provider, implement it as a separate adapter and preserve the existing SISTER API. If the goal is only to compare user-visible workflows, several rows below are functional overlaps despite route and response differences.

## Implementation update (2026-11-03)

SISTER now has local, API-key-protected reference endpoints for territory, Conservatorie, and courts under `/api/v1`. The endpoint paths mirror the territory lookup workflow, while records and IDs remain SISTER-owned; this does not add an Openapi bearer-authenticated provider adapter.

| Local API | Database source |
|---|---|
| `GET /api/v1/territorio`, `/api/v1/territorio/{provincia}`, `/api/v1/territorio/{provincia}/{comune}` | Province names are stored in `territory_province`; municipalities and cadastral codes are read from the shared ISTAT municipalities table. `tipo_catasto=F` or `T` returns sections recorded in the Conservatoria catalog, or `null` when no sections are stored. |
| `GET /api/v1/territorio/conservatorie`, `/api/v1/territorio/conservatorie/{conservatoria_or_id}` | `conservatoria_office`, `conservatoria_municipality`, and `conservatoria_section`, joined to ISTAT municipality records. The optional `comune` parameter returns that municipality's stored sections for both cadastral types. |
| `GET /api/v1/courts`, `/api/v1/courts/{court_id}` | `court` and `court_municipality`, joined to ISTAT municipality records. |

The Alembic revision `20261121_territory_courts` creates the province, court, Conservatoria, coverage, and section tables. It seeds the existing province code/name catalog. Court and Conservatoria records are not seeded: the database did not contain an authoritative catalog, and the old `land_registry_office` rows describe provincial territorial offices rather than Conservatorie. Their APIs return an empty `data` list until curated records are loaded. The Agenzia delle Entrate [Archivio Comuni](https://arcom.agenziaentrate.gov.it/CitizenArCom/) reports cadastral and real-estate registry competence per municipality; Justice court competence is published through [Giustizia Map](https://www.giustizia.it/giustizia/it/mg_form_view.wp?uid=G_MAP). These are candidate authoritative sources for a separately reviewed data import.

## Sources and version notes

- [Openapi Catasto documentation](https://console.openapi.com/it/apis/catasto/documentation)
- [Published Catasto OpenAPI document](https://console.openapi.com/oas/it/catasto.openapi.json)
- Local implementation: `sister/main.py`, `sister/client.py`, `sister/query_forms.py`, and `sister/web.py`

The earlier comparison snapshot recorded `info.version` **3.5.0**, 29 paths, and 35 operations. The published raw document now declares OpenAPI **3.0.0** and `info.version` **3.0.0**; this may be a contract rollback or a versioning mismatch. Do not plan or generate code from the earlier counts. The implementation plan below begins by saving the raw document, its retrieval date, and a content hash, then reconciling the console documentation with that artifact.

The query catalog defines 22 SISTER commands: five use typed client methods and the generic route handles the generic-search forms. SISTER also exposes request polling/history and persisted multi-step workflows. Its client defaults to the local service and sends `X-API-Key`; the published Catasto spec declares HTTP bearer authentication. No direct Openapi Catasto client was found in the inspected modules. This is a material integration boundary, not just a naming difference.

## Cross-cutting differences

| Area | Openapi Catasto | SISTER | Effect |
|---|---|---|---|
| Authentication | Bearer token (`bearerAuth`). | Local API key (`X-API-Key`) for service routes when configured; authenticated web/session routes for user-facing JSON actions. | Existing clients cannot switch base URL and keep working. Use separate credentials and auth handling. |
| Submission and polling | Provider POST operations are documented as asynchronous in production and synchronous in sandbox; resource families have their own collection/detail routes. Geo Catasto GET operations are synchronous. | SISTER queues portal work, returns local request IDs, then polls `GET /api/v1/visura/{request_id}`. Workflows have separate persisted lifecycle routes. | Similar async concept for some queries, different statuses, IDs, polling paths, and sandbox behavior. |
| Source and freshness | Openapi's service describes structured cadastral data and official-document services. | SISTER's query API targets SISTER portal forms and stores local request/results/documents. | A cached or previously archived SISTER result must not be represented as a live Openapi response. Surface source and retrieval time if combining data. |
| Billing and confirmation | Provider operations use the provider's own account, scopes, and charging rules. | The web query proxy has SISTER-side quote/credit confirmation for non-admin users; the local service API has its own key boundary. | Do not assume SISTER's UI quote is an Openapi quote. Provider cost and entitlement handling would need its own adapter path. |
| Response and error contracts | Provider-specific schemas, error codes, and document responses in the published spec. | SISTER-specific queued/cached/completed envelopes, local errors, and stored-document routes. | Normalize only at an explicit adapter boundary; do not silently coerce provider errors or document states into SISTER statuses. |

## Feature parity plan

The target is **functional parity for useful, legally and operationally supportable user tasks**, not a clone of Openapi's account, billing, or infrastructure behavior. SISTER exposes its local Catasto API under `/api/v1/` and keeps SISTER portal automation intact. Add Openapi Catasto behind a separate provider adapter and expose provider-backed tasks through clearly namespaced routes or client methods. A drop-in Openapi-compatible HTTP facade is a separate decision and is not required to reach feature parity in SISTER's product.

Work is ordered by dependency; the phases are release gates, not calendar estimates.

### Release-wide acceptance

- The capability comparison table is maintained as an operation-level matrix with one of `complete`, `partial`, `deferred`, or `not applicable` and links to implementation/evidence.
- No endpoint reports a SISTER portal result as an Openapi result. Responses retain provider IDs, source, retrieval time, and provider error detail.
- Existing SISTER clients now call `/api/v1/visura/*`; provider routes/clients use separate auth, billing, and lifecycle configuration.
- Contract tests use pinned schemas and mocked responses; sandbox smoke tests cover provider behavior. Production calls are enabled only after scope, entitlement, price, and user-confirmation behavior are reviewed.
- Update the OpenAPI snapshot and this gap table before each provider release; a changed upstream schema blocks code generation/release until reviewed.

### Explicitly out of scope unless separately requested

- Replacing SISTER portal automation or silently routing existing SISTER query calls through Openapi.
- Copying Openapi user/account identity, internal IDs, payment ledger, scopes, or callback management into SISTER as if those were shared resources.
- Reproducing an Openapi operation that has no supported SISTER user task, lawful data basis, or available provider scope; record that decision as `not applicable` or `deferred` in the matrix.
