## 0. Scope, constraints and caveats

- **Read-only on the portal side.** No query was submitted, and no `/web/browser/*`, `/web/documents/rescan`, `/shutdown`, or `POST /visura*` call was made — they would drive the live SISTER/CIE session. Findings about those endpoints are **inferred from code**, and say so.
- **Not tested:** the `admin@`, `marialuisa` and `emanuele` accounts (only the least-privileged demo account was used), login rate-limiting / lockout (would risk locking an account), the CAPTCHA flow, multi-step workflow execution, batch mode, CSV export, Tabulator column/filter interaction beyond rendering, planimetry/GeoJSON viewers, and printing.
- **Contrast numbers** come from a script that computes WCAG ratios from computed colours. It cannot read CSS gradients, so white text on the gradient hero banners / primary buttons reports ~1.0:1. Those are **false positives and are excluded** below. Ratios marked *(est.)* were estimated by hand.
- The first crawl ran **unauthenticated**; this turned out to be a finding in itself (A1).
- Credentials for the demo login came from `/mnt/mobile/git/aecs4u.it/local_users.txt` as instructed. They are deliberately **not** reproduced here.
- Screenshots `document_387_*.png` show a real land-registry record containing personal data (names, tax codes, a birth date). **Do not commit or share them.** `docs/ui_audit_2026-10-09/` is git-ignored (`*.png`), so they cannot be committed by accident.

**Severity:** 🔴 Critical (security/data exposure or feature broken) · 🟠 High · 🟡 Medium · 🔵 Low / polish.

## 3. A — Security & authentication

### 🔴 A1 — Web UI is fail-open (anonymous access to data and documents)
**Evidence.** Anonymous `curl`/browser requests returned 200 for `/web/`, `/web/results`, `/web/documents`, `/web/documents/387`, `/web/documents/387/view` and `/download` (108 KB PDF), `/web/dossiers`, `/web/browser` and `/web/browser/status`. `/auth/me` and `/visura/history` correctly returned 401, so auth works; the web routes just don't use it.
**Causes (both required to fix):**
1. `.env` has `REQUIRE_AUTHENTICATION=false`. With that value the `RedirectToLogin` exception handler is never registered ([sister/main.py:270-299](../sister/main.py#L270)).
2. `_require_auth` ([sister/web.py:1238](../sister/web.py#L1238)) wraps `get_current_user` in `except Exception:` and returns `None` ("allow in dev mode"). That also catches the `HTTPException(401)` / `RedirectToLogin` the dependency raises, so **setting `REQUIRE_AUTHENTICATION=true` alone does not fix it.**
**Fix.** Use `aecs4u_auth.dependencies.get_current_user_or_redirect` (exists, [dependencies.py:675](/opt/venv/.aecs4u_venv/lib/python3.12/site-packages/aecs4u_auth/dependencies.py)) directly as the route dependency, remove the blanket `except`, and fail **closed** in anything but an explicit `ENVIRONMENT=development`. See §10.

### 🔴 A2 — Write-capable routes inherit the fail-open check *(inferred from code, not exercised)*
All 11 non-GET web routes depend on `_require_auth`: `/web/browser/{start,stop,restart,launch-chrome}`, `/web/api/batch`, `/web/api/workflow/stream`, `/web/api/{endpoint}`, `/web/documents/{retrieve-missing-pairs,rescan,export-named}`, `/web/results/refresh`. Impact: anyone who can reach port 8025 could drive the logged-in CIE session through the web UI, queue portal queries, or restart the browser. **Correction:** the `/visura*` API and `/shutdown` are *not* open — `.env` defines `API_KEY` and `SHUTDOWN_API_KEY` and the running service answers 401 to anonymous and wrong-key POSTs on `/visura`, `/visura/soggetto`, `/visura/persona-giuridica`, `/visura/workflow`, `/visura/queue/clear` and `/shutdown` (the *"API_KEY non configurata"* warning in `logs/visura.log` dates from 2026-10-06).

### 🟠 A3 — No authorisation tiers on operational pages
The demo (non-admin) account sees the same Browser Control panel (start / restart / **Force** stop) as anyone. crowdaction gates admin-only panels by role (`PanelAuthMiddleware`, `_ADMIN_ONLY_PANELS`). Browser Control and Import Outputs should be admin-only.

### 🟠 A4 — Login form degrades unsafely without JavaScript
`<form method="get">` with no `action` ([login page](../sister/templates), shot: `login_1440`). With JS the submit is intercepted and sent as a JSON `POST` (verified), but without JS the browser would put username **and password in the URL query string** (history, proxy and server logs). Set `method="post"` and an explicit `action`.

### 🟠 A5 — Hardening gaps vs. the sibling app (verified from headers)
- `Content-Security-Policy` allowed `'unsafe-inline'` **and** `'unsafe-eval'` for scripts (crowdaction uses a per-request nonce). *Fixed: see the third pass in §1b.*
- Session cookie `aecs4u_session`: `httpOnly`, `SameSite=Lax`, 24 h, but **not `Secure`** (acceptable on http://localhost, must change behind TLS).
- The logout page posts `X-CSRF-Token: ''` (empty) — CSRF tokens are not wired into the templates (crowdaction provides `csrf_input()` / `require_csrf` / `require_csrf_header`).
- The `POST /auth/logout` carries no CSRF token (the `GET` link only shows a confirmation page, so the risk is low thanks to `SameSite=Lax`, but it is inconsistent with the protected-forms model above).
- `/docs` and `/openapi.json` (50 KB, full route map) are public; crowdaction disables them when `is_production`.
- Two `cookie_consent` cookies are set (host-only and `localhost`-scoped duplicates).
- Rate limiting is not requested in `setup_auth(...)` ([main.py:271](../sister/main.py#L271)); crowdaction passes `enable_rate_limiting=True`. *(Not tested for lockout.)*
- Plain-text credential store: `local_users.txt` holds `username password` pairs in clear, with trivially weak, shared passwords. Acceptable for a dev seed only.

### 🟡 A6 — Logout flow is confusing, unbranded, and calls a third party
1. `Logout` in the user menu → `/auth/logout`, a confirmation page titled **"Logging out…"** that does nothing until a second click on **Sign out**. I waited 12 s: still authenticated, no request fired. [shot: `logout_confirm`]
2. The page is unstyled (default browser button, serif/sans text on the login gradient, no header, no theme).
3. On confirm it loads `@clerk/clerk-js` from jsDelivr and calls `finer-alien-36.clerk.accounts.dev` (two requests, sets `__clerk_db_jwt*` / `__cf_bm` / `_cfuvid` cookies) **even though `USE_CLERK_AUTH=false`**.
4. Once clicked, it works: `POST /auth/logout` → 200, cookie cleared, `/auth/me` → 401, redirect to `/auth/login`. A direct `POST` also works.

### 🔵 A7 — Login UX details
- Wrong password → `401`, generic "Invalid username or password" in a `role="alert"` (good), but focus drops to `<body>`, the 401 is logged as a console error, and there is no inline field state. [shot: `login_wrong_password`]
- No "forgot password" link on the sign-in page although `/auth/forgot-password` exists; no show-password toggle; no "remember me".
- Post-login lands on `/web/` regardless of any `next` (not tested with a protected deep link because A1 means none is protected).
